# Design

## Context

Мотивация и границы описаны в [proposal.md](proposal.md), поведение — в [specs/app-shell/spec.md](specs/app-shell/spec.md).

В `SettingsScreen` версия и GitHub сейчас выводятся внизу страницы; версия берётся из `VITE_APP_VERSION`, который `vite.config.ts` получает из окружения или `package.json`. Релизная сборка передаёт тег с `v`, локальная и контейнерная используют версию пакета. Уже есть удаление префикса для показа версии.

`AppRoutes` использует ленивые страницы со скелетонами. `src/app/layout/use-active-nav-section.ts` определяет режим каркаса и активный раздел; сейчас только точный `/settings` относится к настройкам. PWA кеширует JS сборки, поэтому включённые в чанк данные доступны офлайн. Автотестового фреймворка в проекте нет.

`CHANGELOG.md` содержит заголовки `## [X.Y.Z] - YYYY-MM-DD`, группы `Added`, `Changed`, `Fixed`, маркированные списки, вводные абзацы, жирное выделение и фрагменты кода. В `1.0.0` есть абзац «Первый стабильный релиз», в `0.1.0` — только абзац об историческом релизе. Существующий скрипт GitHub Release читает раздел нужной версии и добавляет коммиты; его менять не требуется.

## Goals / Non-Goals

**Goals:**

- Получать данные непосредственно из корневого changelog, без копирования описаний в TS/JSON и без сетевого запроса в браузере.
- Один раз отредактировать прежние описания в том же `CHANGELOG.md`, сохранив фактическую историю и важные предупреждения.
- Отделить подготовку данных в окружении сборки от отображения в React; не включать Markdown-парсер в клиент.
- Использовать действующие компоненты каркаса и дизайн-токены, сохранив FSD и ленивую загрузку.
- Сформулировать правила редактирования будущих записей так, чтобы при реализации новой возможности не возникала история её промежуточных ошибок.

**Non-Goals:**

- Универсальный Markdown-движок, CMS, новая тестовая инфраструктура или библиотека для semver.
- Хранение истории в пользовательском сторе, отметок прочитанного или версии последнего просмотра.
- Автоматическая оценка понятности текста либо определение по Git, в каком релизе возник баг.

## Decisions

### 1. Подготовка данных при сборке

Локальный помощник в `build/` читает `CHANGELOG.md` и преобразует его в типизированные записи: версия, календарная дата, последовательность абзацев и групп со списками. Небольшой Vite-плагин в `vite.config.ts` предоставляет данные через виртуальный модуль, который импортируется только виджетом истории. Декларация модуля размещается в `src/`; типы помощника также проверяются конфигурацией TypeScript для сборки.

Модуль экспортирует данные, а не HTML. Сгенерированный файл не записывается в исходники и не коммитится. Плагин учитывает исходный changelog как зависимость для обновления данных при разработке. В продуктивной сборке данные входят в граф JS-чанков и существующий precache PWA; отдельного запроса за `.md` или JSON нет. При проверке сборки нужно подтвердить, что чанк истории действительно включён в precache.

Альтернативы: импорт `?raw` с разбором на клиенте добавляет работу браузеру; отдельный JSON требует предварительной генерации и синхронизации; GitHub API нарушает офлайн-сценарий. Виртуальный модуль позволяет использовать существующий цикл Vite без новых зависимостей и команд подготовки.

### 2. Ограниченный формат и сохранение содержания

Парсер поддерживает реально используемый формат: заголовки номерных версий и `[Unreleased]`, стандартные группы Keep a Changelog, абзацы, пункты списков с продолжениями строк, inline-код и жирное выделение. Вступление до версий и весь `[Unreleased]` исключаются. Пустые группы не попадают в результат. Вводные абзацы и порядок пунктов/групп внутри версии сохраняются. Парсер передаёт подготовленные редактором записи, включая `0.1.0`, и сам не переписывает и не фильтрует их по содержанию.

Inline-содержимое представляется текстовыми токенами и React-элементами `strong`/`code`; произвольный HTML не исполняется. При неподдержанном блоковом синтаксисе, неизвестной группе, неверной дате или повторе версии подготовка завершается явной ошибкой с указанием места в changelog. Молчаливое удаление нераспознанных записей недопустимо. Текст `[Unreleased]` не нужно разбирать как опубликованные записи.

Заголовки групп переводятся через namespace виджета: «Добавлено», «Изменено», «Исправлено», «Удалено», «Устарело», «Безопасность». Сами описания остаются русским содержимым changelog и не дублируются в переводах. Полноценный Markdown-рендерер не нужен для текущего файла и добавил бы зависимость без потребности.

### 3. Привязка к версии сборки

Для сравнения используется то же значение версии, что для `VITE_APP_VERSION`: после удаления необязательного начального `v` сравниваются числовые тройки major/minor/patch. Сортировка тоже числовая: `2.10.0` новее `2.9.0`. Включаются только номерные разделы не новее версии сборки. Git-теги и даты не используются как дополнительный реестр опубликованных версий: источником служит сам changelog.

Если номерных записей нет или все они новее сборки, возвращается пустой список для предусмотренного состояния экрана. Отсутствие точного раздела версии не является ошибкой: локальная разработка может опережать оформление релиза. Некорректная версия сборки — явная ошибка подготовки, без подстановки выдуманной версии.

Дата — календарная `YYYY-MM-DD`, а не момент UTC. Отображение «7 ноября 2026» не должно сдвигать день при смене часового пояса. Данные привязаны к конкретной сборке: отложенное обновление не подменяет историю уже работающей версии.

### 4. Размещение в FSD и навигация

| Слой | Изменение |
|---|---|
| App | Маршрут `/settings/changelog`, ленивый импорт, скелетон в `route-fallbacks.tsx`, дополнение `useShellMode` и `useSideNavSection` в `use-active-nav-section.ts` |
| Pages | `pages/changelog` — тонкая страница с публичным `index.ts`, композиция виджета |
| Widgets | `widgets/changelog-screen` — чтение виртуального модуля, список версий, пустое состояние, переводы и публичный API; `widgets/settings-screen` — ссылка в существующем подвале |
| Shared | Переиспользуются `PageHeader`, `PageHeaderBackLink`, `ScreenBody`; новые доменные сущности, стор и storage не добавляются |
| Сборка | `build/` и `vite.config.ts` — подготовка данных, вне клиентских слоёв FSD |

На телефоне используется режим `fullscreen`; на десктопе остаётся стандартный каркас с активными настройками. Экранная кнопка возврата — обычная внутренняя ссылка на `/settings`, а не безусловный `history.back()`, чтобы прямой вход тоже работал. Ссылка из настроек — роутерная, с учётом существующего basename для GitHub Pages.

Одноколоночная лента показывает версии целиком: номер как заголовок секции, дата вторичным текстом, ниже абзацы и списки групп. Без аккордеонов и дополнительного состояния. Для длинного текста используются существующие `text-body`/`text-body-s`, поверхности и отступы; inline-код переносится и не расширяет экран. Светлая/тёмная темы, клавиатурный фокус и зона касания от 44 px обеспечиваются действующими правилами. Собственный скелетон повторяет заголовок и несколько блоков версии; ошибки чанка обрабатывает существующий `RouteErrorBoundary`.

### 5. Правила ведения changelog

В разделе «Сопутствующая документация» `AGENTS.md` при реализации добавить следующие правила:

- Changelog предназначен для пользователей: описывать, что появилось, изменилось или стало работать правильно, простым языком. Не включать внутренний рефакторинг, имена файлов, библиотек и инструментов или другие подробности реализации. Техническое изменение упоминать через его понятный пользовательский результат.
- Описывать итог относительно предыдущей выпущенной версии, а не ход разработки. Ошибки, появившиеся и исправленные внутри одного релиза, не оформлять отдельными исправлениями; уточнять исходный пункт о новой возможности. В `Fixed` включать проблемы, существовавшие в ранее выпущенных версиях.
- Перед выпуском просматривать `[Unreleased]`, объединять дубли и убирать промежуточные состояния разработки.

Эти правила применяются к будущим записям и к разовой редактуре прежних описаний в рамках этого изменения. В спецификации закрепляется понятное пользователю содержание истории; порядок работы редактора остаётся в `AGENTS.md` и задачах. Новая запись об истории изменений сама должна следовать этим правилам.

### 6. Разовая редактура существующей истории

Редактировать непосредственно `CHANGELOG.md` до проверки экрана на окончательном содержимом. Сохранить заголовки версий и даты, формат Keep a Changelog, все значимые пользовательские возможности, реальные исправления и ограничения. Дубли и длинные перечисления можно объединять внутри того же релиза; переносить возможности между версиями или придумывать новые результаты нельзя.

Примеры направления редактуры, а не обязательные дословные замены:

- `GHCR`, теги образов и Compose заменить кратким описанием возможности разместить приложение на своём сервере.
- Имена библиотек, команды проверок, пути файлов и внутренние причины сбоев исключить; оставить, что пользователь теперь может сделать и какая проблема устранена. Записи только о внутренней разработке без пользовательского результата удалить; не заменять их выдуманным улучшением.
- Из длинного описания дизайн-системы оставить наблюдаемые изменения оформления, удобства и читаемости без названий шрифтов, токенов и CI.
- В записях о резервных копиях убрать номера форматов, сохранив предупреждения о загрузке старых копий и несовместимости новых с прежними приложениями. Сохранить ограничения отката, установки и переноса данных, если они влияют на пользователя.
- Историческую запись `0.1.0` сократить до пояснения, что версия не была доступна на сайте и заменена `1.0.0`, без подробностей деплоя.

Исправления промежуточных ошибок новой функции объединять с её описанием только при подтверждении по истории соответствующих релизных тегов, коммитов или архивных артефактов. По одному стилю записи или совпадению дат вывод не делать. Если происхождение ошибки не подтверждено, сохранить описанный пользовательский результат, убрав техническое объяснение, и отметить неопределённость в отчёте.

После редактуры сверить исходный и новый changelog: набор версий и дат тот же, возможности не приписаны другим релизам, значимые предупреждения не потеряны. Для каждой удалённой или объединённой записи проверить, что это внутренние подробности, дубль либо подтверждённый промежуточный этап. В интерфейсе и GitHub Release для будущего выпуска используется один и тот же файл. Прежние GitHub Releases и теги не изменяются; старые опубликованные сборки сохранят свою историю.

## Risks / Trade-offs

- [Небольшой парсер поддерживает ограниченный синтаксис] → Покрыть текущий файл и целевые пограничные случаи; выдавать понятную ошибку при расширении формата, не теряя текст молча.
- [При упрощении старой записи потеряют важное ограничение или реальное исправление] → Сверить старую и новую формулировки; сохранить пользовательский смысл, совместимость и даты, а неподтверждённое происхождение ошибки не трактовать как промежуточный этап.
- [История растёт и увеличивает сборку] → Данные импортируются только ленивым экраном, без Markdown-библиотеки; при текущем размере файла пагинация и виртуализация не нужны.
- [Офлайн-сценарий ошибочно проверят только после посещения экрана] → Отдельно проверить precache и первое открытие истории без сети после кеширования основной страницы.
- [Новую возможность ошибочно опишут вместе с её внутренними исправлениями] → Проверять `[Unreleased]` по правилам `AGENTS.md` перед выпуском; автоматическое восстановление истории разработки не требуется.

## Migration Plan

Обычный выпуск статической PWA: отредактированный changelog и код публикуются одной сборкой. Прежние теги и GitHub Releases не перепубликуются. IndexedDB, localStorage и формат бэкапа не меняются; `docs/domain.md` не требует обновления. В `docs/architecture.md` добавляются новый маршрут, слайсы и путь подготовки истории. При откате на предыдущую версию исчезает экран истории, пользовательские данные остаются в прежнем формате.
