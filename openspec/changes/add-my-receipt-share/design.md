# Design

## Context

- Счёт (`PersistedBill`) уже умеет то, что нужно чеку после расчёта долей:
  - балансы и переводы — чистые функции в целых копейках (`entities/debt/model/bill/compute-bill.ts`);
  - долги с `billId` создаются и пересчитываются атомарно (`createBill` / `updateBill` → `putBillWithDebts`);
  - статус выводится из долгов;
  - подписи участников, сводка последствий, удаление и метка «Из счёта» уже работают.
- Форма `features/create-bill/BillForm`: шаг 1 (`BillBasicsSection`: сумма, валюта, описание, участники, «Кто заплатил» с `PayerSheet`) и шаг 2 (`BillSplitSection`: «Как делим» и итог). Состояние формы — `use-bill-form.ts` (`BillFormState`, `toDraft` → `BillDraft`). Та же форма обслуживает изменение и изменение после погашений (`locked`).
- `updateBill` сопоставляет долги по паре (`contactId`, `direction`): смена плательщика или состава сама даёт «удалить лишние, создать недостающие».
- Резервная копия — версия 2, импорт принимает 1 и 2 (`shared/lib/storage/backup.ts`). IndexedDB — версия 2, стор `bills` без схемы полей.

## Goals / Non-Goals

**Goals:**
- Деление по чеку — способ деления того же счёта: переводы, долги, статус, экран, изменение и удаление без параллельной ветки логики.
- Доли считаются точно по всему чеку и детерминированно; сумма долей всегда равна итогу.
- Быстрый случай «сколько с меня» (два участника и люди без имени) и полный «кто сколько должен» — один и тот же экран.

**Non-Goals:**
- Несколько плательщиков в режиме «По чеку»: итог неизвестен, пока не внесены позиции, а сверка оплат с итогом вернула бы ввод итога первым.
- Отдельная форма или слайс для чека.
- Новые сторы или индексы IndexedDB.

## Decisions

### 1. Чек — `Bill` со `splitMode: "items"`

`BillSplitMode` получает значение `"items"`, `PersistedBill` — поле `items: BillItem[]` (`[]` у остальных способов деления).

- Альтернатива — отдельная сущность `Receipt`. Отвергнута: дублировала бы участников, переводы, статус, удаление и связь долга (`billId`).

### 2. Позиция: отмеченные участники и люди без имени

```ts
type BillItem = {
	id: string;
	title: string | null;
	price: number;        // за всю строку
	refs: string[];       // отмеченные участники счёта, в порядке participants
	extraPeople: number;  // люди без имени, 0…99; «на скольких» = refs.length + extraPeople
};
```

- `participants[i].inSplit` для `"items"` вычисляется при сохранении: участник отмечен хотя бы в одной позиции. Так существующие проверки «кто участвует» и «Я не участвую» работают без изменений. `shareInput` — `null`. `paid` — вся сумма у единственного плательщика.
- `totalAmount = Σ price` вычисляется в сторе из позиций, а не берётся из ввода.

### 3. Режим — переключатель внутри `BillForm`, а не отдельная форма

- `BillFormState` получает `entry: "sum" | "receipt"` (по умолчанию `"sum"`) и `items: FormItem[]` (цена — сырая строка, как остальные суммы формы). `splitMode` остаётся выбором «Как делим» для режима «Одной суммой»: при возврате из «По чеку» он восстанавливается.
- `toDraft` для `"receipt"` даёт `splitMode: "items"`, `totalAmount` = итог позиций, оплату целиком у `payerRef`. При входе в `"receipt"` из `payerMode: "several"` выбирается участник с наибольшей оплатой. В `"receipt"` `payerMode` всегда `"one"`.
- UI:
  - переключатель режима — первым в `BillForm`; в режиме чека `BillBasicsSection` показывает «Сумма по чеку» с итогом вместо поля суммы, без переключателя «Один / Несколько»;
  - `PayerSheet` — без «Платили несколько» в режиме чека;
  - новый `BillItemsSection` — позиции: чипы-отметки с первым словом имени, «+ ещё» и счётчик −/+, `AmountInput` для цены;
  - новый `BillReceiptShares` — «Доли» (участник, доля, подпись по `describeParticipant`), строки о людях без имени и копейках, общая сводка последствий;
  - режим чека на телефоне — один экран без шагов (по макетам `SplitReceipt*`): основные поля, позиции, доли, «Сохранить счёт»; на десктопе — колонки «1 · Кто участвует и платил» с долями и «2 · Позиции · N» (`DeskSplitReceipt`);
  - удаление участника на шаге 1 убирает его `ref` из всех позиций.
- Маршруты и меню «+» не меняются: создание всегда начинается в «Одной суммой», `pages/edit-bill` берёт режим из `bill.splitMode`.
- Альтернатива — отдельный слайс `create-receipt` (первая версия этого change). Отвергнута: с именами в позициях ему нужны участники, шторка плательщика, итог и сводка, то есть почти вся `BillForm`.

### 4. Расчёт долей и переводов

- `computeBillShares` для `"items"`:
  - для каждого участника и для людей без имени — точная дробь Σ `price_cents / N` по позициям, где они делят строку (`BigInt`, общий знаменатель — НОК различных N);
  - пол каждой доли в копейках, затем оставшиеся копейки раздаются по наибольшему дробному остатку; при равенстве — по порядку `participants`, люди без имени последними;
  - результат — `cents` по участникам и новое поле `BillShares.othersCents`.
- Переводы: доля людей без имени при расчёте балансов относится к плательщику (баланс плательщика = итог − его доля − `othersCents`). Сумма балансов остаётся нулевой, `minimizeTransfers` получает только именованных участников, и при одном плательщике переводы — «каждый должник → плательщик». Ни в `transfers`, ни в `participants` нет виртуального участника, поэтому `groupBillTransfers`, `describeParticipant`, `describeConsequences`, `computeMyBillDebts` и `computeBillMyTotals` работают без изменений.
- `validateBill` для `"items"`: `amount_required` (нет позиций с ценой), `participants_min`, новые `item_price_required` / `item_people_required` со списком индексов строк; `paid_mismatch` и `split_mismatch` не применяются. Пустые строки отбрасывает форма в `toDraft`.
- Альтернатива — округлять каждую строку и раздавать её копейки по порядку. Отвергнута: на чеке из 10–15 позиций лишние копейки копятся у первого участника.
- Альтернатива — виртуальный участник «без имени» в переводах. Отвергнута: при одном плательщике он ничего не даёт, а каждый потребитель переводов пришлось бы научить его пропускать.
- Альтернатива — `Number` с суммированием дробей. Отвергнута: на половинах копейки двоичная погрешность делает округление недетерминированным.

### 5. Экран счёта и подписи

- `widgets/bill-detail`: для `"items"` — блок «Позиции N» над «Кто кому переводит» (больше пяти позиций — четыре и «Показать все N позиций») и строка «Ещё X — доли людей без имени…» по `othersCents`. Остальное существующее: «Участники» с «оплата · доля», переводы, прогресс, пояснения, кнопки. Название способа деления «По чеку» — в переводах виджета рядом с «Поровну».
- `entities/debt/ui/BillParts`: «<сумма> по чеку» вместо «<сумма> на <N>» в строке на главной и метке на долге. Число людей в чеке с учётом людей без имени неточно, поэтому «на N» здесь вводило бы в заблуждение.

### 6. Хранилище и резервная копия

- Версия IndexedDB не меняется. Отсутствующее `items` нормализуется в `[]` в `hydrate` и `createDebtsBackup`, как сейчас `billId`.
- `BillInput` получает `items`. В `createBill` / `updateBill` для `"items"` проверяются:
  - есть позиции;
  - цена > 0;
  - N ≥ 1 и `extraPeople` в 0…99;
  - `refs` — участники счёта;
  - единственный плательщик.
  При погашениях `updateBill` сравнивает и позиции (как сейчас участников): изменить можно только описание.
- Резервная копия пишется версией 3. `parseDebtsBackup` принимает 1, 2 и 3, у счетов копий 1 и 2 ставит `items = []`. Копия версии 3 со счётом `"items"` без массива позиций — неверный формат.

### 7. Скидка и чаевые

Решения брифа 2 (`design-brief-2.md`) и макетов `SplitReceipt*`, `RcAdjust`.

```ts
type BillAdjustmentUnit = "percent" | "amount";
type BillDiscount = { unit: BillAdjustmentUnit; value: number };
type BillTips = { unit: BillAdjustmentUnit; value: number; refs: string[]; extraPeople: number };
// PersistedBill.discount: BillDiscount | null; PersistedBill.tips: BillTips | null — null у остальных способов деления
```

- Хранится введённое значение (процент или сумма), а деньги выводятся: тот же ввод всегда даёт тот же расчёт, а экран счёта показывает «Скидка 10 %».
- Деньги в копейках (`computeReceiptCents`):
  - S — сумма позиций;
  - скидка D — `round(S × p / 100)` или сумма, 0 < D < S;
  - чаевые T — `round((S − D) × q / 100)` или сумма, T > 0;
  - итог `totalAmount` = S − D + T: его платит плательщик, его показывают главная и метка на долге.
- Доли — точные дроби на `BigInt` с общим знаменателем `НОК(N позиций, N чаевых) × S`:
  - позиции умножаются на (S − D) / S;
  - чаевые — T / N у отмеченных и людей без имени;
  - округление по-прежнему одно на весь чек.
- `inSplit` участника — отмечен в позиции или в чаевых.
- Новые ошибки `validateBill`: `discount_invalid`, `tips_invalid`, `tips_people_required` блокируют переводы и сохранение. Стор проверяет то же и отклоняет `refs` чаевых не из участников.
- Форма хранит значение сырой строкой и флаг «открыто». Открытие ставит 10 %, у чаевых — все участники. Смена «% / ₽» пересчитывает значение в те же деньги: сумму — в копейках, процент — до двух знаков.
- Альтернатива — чаевые пропорционально долям. Отвергнута: у чаевых свой выбор, кто делит, и подпись «по X» понятнее.
- Альтернатива — скидка на часть позиций. Отложена: флаг на позиции, когда понадобится.

### 8. Форма без прыжков

- Доли и сводка в форме считаются по «черновику для показа»: незаполненные позиции и скидка или чаевые с ошибкой из него убраны. Проверка и сохранение идут по полному черновику, поэтому кнопка остаётся неактивной. Пропущенные строки перечисляются «Позиция N пока не учтена».
- Отметки — видимая высота 32 px, зона касания 44 px, одна ширина в обоих состояниях (кружок с галочкой или пустой). «+ ещё» и счётчик — 128 px.
- Подпись под позицией и строка состояния над кнопкой — одна строка с многоточием, место под строку есть всегда.

## Risks / Trade-offs

- [«по X» в строке позиции не складывается в долю участника до копейки] → доля считается по точной дроби, пояснение о неделимых копейках показывается, когда они раздавались.
- [Доля людей без имени «повисает» на плательщике] → это честное описание ситуации: эти деньги собирает плательщик вне приложения. Под итогом и на экране счёта показывается строка с суммой.
- [Переключение режима в форме с введёнными позициями и сохранение в «Одной суммой»] → позиции не сохраняются, сохраняется только выбранный режим. Поле суммы подхватывает итог позиций, чтобы переход не обнулял ввод.
- [`BillForm` растёт] → позиции вынесены в отдельный `BillItemsSection`, логика режима — в `use-bill-form`, расчёт — в сущности.
- [Прежняя версия приложения откроет базу со счётом по чеку] → откат PWA не предусмотрен. Копию версии 3 прежние версии отклонят как неверный формат.

- [Значение скидки в процентах хранится, а не деньги] → при изменении позиций скидка пересчитывается сама; это и ожидается от «10 % на чек».

## Migration Plan

1. Новая версия читает старые счета без `items` (нормализация `[]`), данные не переписываются.
2. Первая запись счёта по чеку добавляет только новые поля в стор `bills`. Отсутствующие `discount` и `tips` нормализуются в `null`.
3. Экспорт пишет копию версии 3; копии версий 1 и 2 импортируются как раньше.
