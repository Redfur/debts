# Design

## Context

- Счёт (`PersistedBill`) уже умеет то, что нужно чеку после расчёта долей: балансы и переводы — чистые функции в целых копейках (`entities/debt/model/bill/compute-bill.ts`), долги с `billId` создаются и пересчитываются атомарно (`createBill` / `updateBill` → `putBillWithDebts`), статус выводится из долгов, удаление и метка «Из счёта» уже работают.
- Форма `features/create-bill/BillForm` начинается с итога и сверяет с ним оплату и деление. Она обслуживает создание, изменение и изменение после погашений; позиции в неё не встраиваются без перестройки обоих шагов.
- Сопоставление долгов при `updateBill` идёт по паре (`contactId`, `direction`): смена плательщика сама даёт «удалить старый долг, создать новый».
- Резервная копия — версия 2, импорт принимает 1 и 2 (`shared/lib/storage/backup.ts`). IndexedDB — версия 2, стор `bills` без схемы полей.

## Goals / Non-Goals

**Goals:**
- Чек — тот же счёт: статус, долги, удаление, экран, строка на главной и метка на долге работают без параллельной ветки логики.
- Доля пользователя считается точно (без накопления копеек по строкам) и детерминированно.
- Данные позиции уже в форме этапа 2 (имена в позициях): переход не потребует миграции хранилища и копии.

**Non-Goals:**
- Общий движок «позиции с именами и переводы каждому»: в этапе 1 именованный участник позиции только «Я».
- Перестройка `BillForm` и шагов обычного счёта.
- Новые сторы или индексы IndexedDB.

## Decisions

### 1. Чек — `Bill` со `splitMode: "items"`, а не новая сущность

`BillSplitMode` получает значение `"items"`, `PersistedBill` — поле `items: BillItem[]` (`[]` у остальных способов деления).

- Альтернатива — отдельная сущность `Receipt` со своими долгами. Отвергнута: пришлось бы дублировать статус, удаление, связь долга (`billId`), метку на карточке и секцию на главной.

### 2. Форма позиции: отмеченные участники + люди без имени

```ts
type BillItem = {
	id: string;
	title: string | null;
	price: number;          // за всю строку
	refs: string[];         // отмеченные участники; в этапе 1 всегда ["me"]
	extraPeople: number;    // ещё людей без имени; «на скольких» = refs.length + extraPeople
};
```

- Альтернатива — `people: number` с неявным «я внутри». Проще сейчас, но этапу 2 понадобилась бы миграция всех чеков.
- «На скольких» ограничено 1…99 и в форме, и в сторе.

### 3. Участники чека и итог

Чек хранит `participants = [{ ref: "me", paid: 0, inSplit: true }, { ref: <плательщик>, paid: total, inSplit: false }]` (`shareInput: null`), `totalAmount = Σ price`. Итог вычисляется в сторе из позиций, а не берётся из ввода.

Так существующие потребители (`computeBillStatus`, `computeBillMyTotals`, текст удаления, «Платили: …») работают без изменений. Плательщик не входит в именованное деление: его доля — среди людей без имени, на мой долг это не влияет.

Сборка `BillInput` для чека — хелпер в `entities/debt/model/bill` (`buildReceiptBillInput({ title, currency, payerId, items })`), чтобы инвариант «я в каждой позиции, плательщик платит всё» жил в сущности, а не в форме.

### 4. Расчёт: точная доля и анонимный узел

- В `computeBillShares` для `"items"` доля именованного участника — Σ `price_cents / N` по его позициям, считается как точная дробь (числитель и знаменатель на `BigInt`, общий знаменатель — НОК различных N) и округляется до копейки один раз, половина — вверх. Доля людей без имени — `total − Σ именованных долей`, поэтому сумма долей всегда равна итогу.
- Для расчёта балансов люди без имени — один виртуальный участник `OTHERS_REF` (константа рядом с `ME_REF`), которого нет в `participants`. `minimizeTransfers` получает и его баланс, и переводы остаются нулевой суммой: «Я → плательщик», «без имени → плательщик». `computeMyBillDebts` и `computeBillMyTotals` смотрят только на `ME_REF`, поэтому перевод без имени долгов не создаёт.
- `validateBill` для `"items"`: `amount_required`, если позиций нет или итог 0; `split_mismatch` не применяется (остаток уходит людям без имени). Ошибки строк («Введите цену больше нуля», «Выберите, кто заплатил») — в модели формы.
- Альтернатива — округлять «моё» по каждой строке и складывать. Отвергнута: на чеке из 10–15 позиций расхождение набегает на несколько копеек; спека требует одно округление и пояснение, когда сумма строк расходится с итогом.
- Альтернатива — `Number` с суммированием дробей. Отвергнута: на половинах копейки двоичная погрешность даёт недетерминированное округление.

### 5. UI — отдельный слайс `features/create-receipt`

- `features/create-receipt`: `ReceiptForm` (создание, изменение, изменение после погашений, как у `BillForm`), `use-receipt-form` (строки, валидация, пустые строки отбрасываются), `translations.ts` (namespace фичи). Плательщик — `features/select-contact/ContactPicker`, цена — `shared/ui/AmountField`, валюта — `shared/ui/CurrencyPicker`, счётчик — кнопки «Меньше»/«Больше» по образцу «Долями» в `BillSplitSection`.
- `pages/create-receipt` — маршрут `/bills/new/receipt` (lazy). Он под `/bills/*`, поэтому полноэкранный режим каркаса и подсветка «Главной» в боковом меню получаются без изменений `app/layout`. Статический сегмент имеет приоритет над `/bills/:billId`.
- `pages/edit-bill` выбирает `ReceiptForm` при `bill.splitMode === "items"`, иначе — `BillForm`; признак `locked` считается как сейчас.
- Альтернатива — четвёртый способ в `BillForm`. Отвергнута: итог там вводится первым и сверяется на обоих шагах (см. proposal).

### 6. Экран счёта и подписи

- `widgets/bill-detail`: для `"items"` вместо «Кто кому переводит» и «Участники» — блок позиций с моей частью, мой перевод с отметкой «✓ погашен» (по найденному долгу, как сейчас) и строка «Остальные …». Строка под суммой — «По чеку · N позиций» вместо «<способ> · N участников». Пояснения внизу и кнопки — существующие (у чека всегда есть мой долг).
- `entities/debt/ui/BillParts`: «<сумма> по чеку» вместо «<сумма> на <N>» в строке на главной и метке на долге. «на троих» в позициях — существующий `formatPeopleCount`.
- `app/layout/CreateFab`: третий пункт «Моя часть чека» (иконка `ReceiptText`) → `/bills/new/receipt`, новая подпись «Разделить счёт» — в `shared/i18n` (`common`).

### 7. Хранилище и резервная копия

- Версия IndexedDB не меняется. Отсутствующее `items` нормализуется в `[]` в `hydrate` и `createDebtsBackup`, как сейчас `billId`.
- `BillInput` получает `items`. `updateBill` при погашениях сравнивает и позиции (как сейчас участников): изменить можно только описание.
- Резервная копия пишется версией 3. `parseDebtsBackup` принимает 1, 2 и 3. У счетов из копий 1 и 2 `items = []`. В версии 3 счёт `"items"` без массива `items` — неверный формат.

## Risks / Trade-offs

- [Сумма «моё» по строкам расходится с итогом на копейку] → пояснение под итогом (требование «Моя часть чека»); итог считается по точной дроби.
- [`OTHERS_REF` попадёт туда, где по `ref` ищут контакт] → он появляется только в переводах счёта `"items"`, а экран чека не использует общие функции группировки и подписи участников. Константа не пишется в `participants`; комментарий об этом — в `types.ts`.
- [Прежняя версия приложения откроет базу с чеком] → откат PWA не предусмотрен. Копию версии 3 прежние версии отклонят как неверный формат, поэтому ошибочно её не прочитают.
- [Ссылка «Разделить счёт» в подсказке теряет введённые позиции] → это явно в спеке. Перенос данных между формами не делается: у обычного счёта нет позиций.
- [`BigInt` в расчёте] → поддерживается всеми целевыми браузерами PWA. Вычисление изолировано в одной чистой функции.

## Migration Plan

1. Новая версия читает старые счета без `items` (нормализация `[]`), данные не переписываются.
2. Первая запись чека добавляет только новые поля в стор `bills`.
3. Экспорт пишет копию версии 3; копии 1 и 2 импортируются как раньше.
