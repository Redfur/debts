# Design

## Context

Мотивация и границы — в `proposal.md`, наблюдаемое поведение — в 13 delta-спецификациях этого change.

Проверенный исходный код:

- Backend отсутствует. `Dockerfile` собирает Vite и отдаёт статику nginx; `compose.yaml` запускает один образ без постоянных данных. Release публикует GitHub Pages и один образ GHCR.
- `src/shared/lib/storage/indexed-db-adapter.ts` открывает `debts` native-версии 3 через `idb`: контакты, долги, операции, счета, черновики и `meta`. UUID пригодны для переноса, но `updatedAt` не является причинной версией; удаление физическое, аккаунтного пространства нет.
- `StorageAdapter` содержит низкоуровневые `putDebt`/`putDebtOperation` и несколько составных операций. В `debt-store.ts` изменение исходной суммы и погашение записывают долг и операцию отдельными вызовами: это необходимо заменить одной транзакцией, не просто обернуть запросы сетью.
- Гидрация Zustand читает локальную базу и отдельно запускает курсы. Черновики сериализуют запись по виду и завершаются атомарно с созданием записи. Эти гарантии должны сохраниться.
- Экспорт версии 3 читает таблицы несколькими запросами, импорт 1–3 полностью заменяет базу; сброс настроек и удаление базы не различают владельцев. Нужны согласованный снимок и namespace-aware операции.
- Чистые расчёты счетов и остатков находятся в `entities/debt/model`; денежные значения — `number` с точностью 0,01, расчёты чека используют целые копейки и точные дроби. Go не должен независимо пересчитывать финансовую модель.
- Есть отдельные Node-тесты в `build/`, но нет полноценной инфраструктуры проверки нескольких реплик, миграций и серверного восстановления.

Активный `add-english-and-number-formats` пересекается с настройками, сбросом и PWA. Реализация должна согласовать пересечения до изменения этих участков; этот change не заменяет его требования. Новые тексты колоцированы и используют i18n; если английский уже применён, переводятся на оба языка.

## Goals / Non-Goals

**Goals:**

- Сохранить локальную долговечность и мгновенный интерфейс без сетевого барьера.
- Доказуемо переживать повтор, перестановку, прерывание доставки и параллельные изменения без молчаливого удаления вариантов.
- Разделить локальную проекцию финансовых данных, причинную историю и серверный порядок доставки.
- Сохранить атомарность счетов, операций и переноса ссылок контакта на всех границах.
- Выпустить один открытый self-hosted комплект без обязательного облака.

**Non-Goals:**

- Универсальный движок редактирования произвольных документов, распределённые транзакции между офлайн-устройствами и глобальная блокировка отключённого клиента.
- Серверная авторитетная финансовая модель или общий TS/Go модуль расчётов.
- Непрерывная работа закрытой PWA, универсальная совместимость старых клиентов, автоматическое решение любого конфликта.

## Decisions

### 1. Локальная база и FSD

Оставить Zustand как реактивную проекцию, Dexie сделать единственным рабочим persistence-слоем. Не добавлять параллельную копию финансов в localStorage и не заменять адаптер сетевым.

Предлагаемое размещение:

| Слой | Ответственность |
| --- | --- |
| `shared/lib/storage` | Dexie, версии схемы, отдельные наборы, атомарные транзакции, миграция и формат файлов; без доменного согласования |
| `shared/api` | типизированный HTTP/SSE транспорт, коды ошибок; без доступа к чужому namespace |
| `shared/config` | публичный режим поставки и безопасные параметры установки |
| `entities/debt` | финансовые actions, чистые правила согласования, построение change-set, общая блокировка записи, CRUD/объединение контактов |
| `entities/account` | публичное состояние аккаунта и сеанса; браузер не хранит bearer-секреты в доступном JS хранилище |
| `features` | вход, passkey, привязка, восстановление, выход, управление сеансами, удаление аккаунта; управление контактами, разрешение конфликтов, ручной запуск, подключение набора |
| `widgets` | раздел аккаунта/синхронизации, расхождения, настройки и предупреждения главной |
| `pages` | `/settings/account`, `/settings/sync`, `/settings/conflicts` и детали конфликта; карточки контактов используют прежние пути |
| `app` | выбор набора, гидрация, lifecycle sync coordinator, маршруты и общий баннер |

Features не импортируют друг друга; app/widgets передают действия и собирают сценарии. Контракт общего local write gate находится ниже features, поэтому прямой вызов store, старое окно или другая вкладка не обходят режим просмотра. Проверка запрета и запись происходят в одной транзакции. UI отключение — дополнительная подсказка, не единственная защита.

### 2. Наборы и миграция native IndexedDB

Для изоляции использовать отдельную Dexie-БД каждого набора: `debts-local-<datasetId>`. Маленький реестр на устройстве хранит активный набор и его тип (`guest`/`account`/`recovery`), непрозрачный account ID и идентификатор установки; он не содержит сеансовых секретов. Аккаунтный ключ включает серверную идентичность установки и account ID, не email. Один активный набор на origin согласуется между вкладками.

Таблицы набора:

- существующие финансовые таблицы с прежними UUID и индексами;
- `creationDrafts`, локальный кэш курса;
- `changes`: неизменяемые исходящие/полученные change-set;
- `outbox`: состояние доставки и зависимости по `changeId`;
- `replicaState`: курсор, известный frontier, версии протокола/согласования, server epoch и generation;
- `conflicts`: варианты, причина, охват и решения; `recovery`: сохранённые данные старого поколения или невозможного согласования;
- `contactRedirects`: подтверждённые переадресации объединённых контактов, не переадресация по имени.

Миграция не переименовывает старую БД на месте и не принимает `db.version(3)` за native version 3: Dexie умножает объявленную версию на 10. Старую `debts` читать native IndexedDB в режиме read-only после краткого повышения её native-версии до 4 с одним migration-fence marker. Это закрывает старые соединения через имеющийся `blocking` handler и не даёт старому `idb`-клиенту снова открыть её с версией 3. При блокирующей старой вкладке показывать просьбу закрыть/обновить её, не продолжать частично.

Скопировать согласованный снимок старых таблиц в новый guest DB одной транзакцией, нормализуя `billId`, позиции, скидки и чаевые как прежде; отсутствующие в старых native-версиях таблицы счетов/черновиков считать пустыми. В одной целевой транзакции установить marker завершённого импорта. Переключить реестр только после commit; повтор использует тот же migration ID и не копирует записи второй раз. Старый исходник остаётся для восстановления до проверки целевого набора, но не является вторым активным источником. После проверки можно очистить финансовое содержимое legacy-таблиц, сохранив пустую БД native-версии 4 с fence и marker переноса: удаление всей legacy-БД позволило бы старому коду заново создать базу версии 3. «Очистить всё» не должно оставлять забытую приватную legacy-копию. При ошибке содержимое исходника не очищается; после подтверждённого переноса/очистки marker запрещает повторный импорт.

Черновики 1 и финансовые суммы сохраняются побайтно по смыслу, порядок массивов участников/позиций не сортируется. Нет автоматического создания аккаунта или outbox всей гостевой истории. Понижение приложения после fence не поддерживается; нужен экспорт/чистый профиль.

Альтернатива — compound keys в единственной базе — отвергнута: ошибка фильтра владельца затронет чужие данные и усложнит существующие черновики и wipe. Цена отдельных БД — явно согласованный реестр и очистка всех вкладок.

### 3. Локальная транзакция и проекция

Каждый доменный action захватывает актуальные записи и local write gate внутри транзакции и создаёт immutable change-set. Одна транзакция пишет финансовую проекцию, версию, outbox и при необходимости удаляет черновик. При abort оптимистичный UI откатывает только своё изменение; при сетевой ошибке отката нет.

Составные методы заменить/добавить для изменения долга с initial operation, погашения, счёта с долгами, удаления каскадом и объединения контактов. `replaceAll` доступен только guest/recovery-импорту и не используется для применения серверного снимка поверх активного аккаунта.

Доменная проекция подписана на местные транзакции: синхронизация и другие вкладки обновляют тот же Zustand-снимок после commit. Для вкладок — уведомления и повторное местное чтение; не два независимых write-through стора с устаревшими остатками. Последняя валидация погашения находится внутри DB-транзакции, а не только в React-памяти.

Нельзя ожидать HTTP, OAuth, WebAuthn или длительную криптографию внутри Dexie-транзакции. Сеть — отдельный шаг после commit. Один coordinator на активный набор выбирается через Web Locks, с освобождением при закрытии и восстановлением на следующем запуске; идемпотентный сервер защищает и от случайного двойного отправителя. При недоступности Web Locks используется ограниченный lease в локальной БД с fencing token. Все писатели проверяют dataset activation token, чтобы завершение запроса старого набора не записало данные в новый.

### 4. Протокол: неизменяемые версии, а не серверное выполнение финансовых команд

В отличие от первоначально обсуждённого server-authoritative API, Go принимает **готовые версии финансовых результатов**, а не решает, можно ли применить платёж к своему «главному» остатку. Он проверяет принадлежность, структуру, размеры, допустимые типы и причинные ссылки, но не выбирает победившую ветвь.

Envelope `ChangeSetV1` содержит:

- `protocolVersion`, `schemaVersion`, `mergeVersion`;
- `changeId` (UUID для пользовательского действия), `replicaId`, `generation`;
- `parents`: известные причинные головы набора, включая ещё не отправленные действия;
- `kind`: обычная правка, seed/transfer, merge-contacts, auto-merge certificate или explicit resolution;
- атомарный `writeSet`: полные before/after версии затронутых агрегатов или tombstone, плюс ссылки/read dependencies для согласования межагрегатных связей;
- исходные идентификаторы операций и изменения полей, необходимые для предметного сравнения;
- для решения — точный набор разрешаемых ветвей и выбранный целый результат;
- локальное время для подписи, не для выбора победителя; стабильный digest нормализованного envelope.

Единицы согласованности: обычный долг вместе с историей; счёт вместе со всеми его долгами и историей; контакт. У долга из счёта нет отдельной конкурирующей «истины»: погашение меняет агрегат счёта. Объединение контактов — атомарный write-set контактов и всех затронутых агрегатов; включает зависимости, чтобы concurrent новый долг/участие не оставил отсутствующую ссылку. Перенос нового набора может быть несколькими ограниченными группами с зависимостями; проекция не публикует неполную группу.

Before-состояние и причинные ссылки позволяют вычислить трёхстороннее/многоветочное согласование без предположений по `updatedAt`. Server log — порядок доставки, а не порядок победы. Server acknowledgement означает сохранение envelope, а не признание финансовой ветви единственно правильной.

На сервере хранить уникальность `(account_id, generation, change_id)` и digest. Тот же ID с тем же содержимым возвращает прежнее подтверждение; с другим — явная protocol error. Недостающие родители — `missing_dependencies`, не финансовый конфликт; клиент отправляет родителей и повторяет. У всех зависимостей тот же владелец/generation. Ограничивать число родителей/записей/глубину/размер, отвергать циклы и неподдерживаемые версии.

Суммы протокола передавать целыми minor units с безопасным диапазоном, преобразование из нынешних `number` только после текущего округления до 0,01. Проценты — целые сотые процента. UI/бэкап сохраняют прежний смысл сумм; Go проверяет целочисленный диапазон, не рассчитывает доли. Канонизация envelope сортирует ключи и наборы causal IDs, но никогда не порядок участников/позиций. Одинаковые fixtures в Go/TS проверяют кодирование и digest, а не дублируют денежный движок.

Альтернативы: last-write-wins теряет платежи; только CRUD + WebSocket не даёт повторяемость; общий снимок всего аккаунта для каждой правки создаёт лишние конфликты и трафик. Универсальный CRDT избыточен для ограниченного набора предметных действий.

### 5. Клиентское согласование и конфликты

Чистая модель в `entities/debt/model/sync` обрабатывает весь известный причинный frontier, а не последовательно перезаписывает таблицы в порядке прихода. Для N ветвей вычисляет общую основу и изменения всех ветвей; одинаковый набор envelope даёт один результат независимо от доставки. Матрица разрешённых автоматических случаев фиксирована спецификацией: независимые записи, одинаковый итог поля, совместимые разные поля, note + repayment, union разных repayment IDs в пределах исходной суммы при неизменных условиях.

`status`, остатки и `closedAt` после безопасного union выводятся из целого набора операций; момент закрытия определяется детерминированным порядком операций `(createdAt, id)` для отображения, не используется для победы ветвей. Нельзя брать пришедший `status` отдельно от истории. Финансовые условия против repayment всегда конфликтуют. Разные правки распределения/позиций — выбор целого агрегата; не пытаться сливать массивы «по индексам». Конкурентное удаление контакта/объединение против новых ссылок проверяется при materialization.

При безопасном автоматическом согласовании можно материализовать результат без дополнительной пользовательской записи. Если нужен сохранённый merge certificate для сокращения frontier, его ID/digest определяется версией алгоритма и отсортированными родителями, чтобы клиенты не плодили бесконечные дубли. Он не уничтожает исходные ветви. Разные версии merge engine не обмениваются такими сертификатами без согласования совместимости.

Конфликт имеет стабильный ID по причине и охваченным причинным версиям, варианты, известную основу и локальную provisional projection. Открытый конфликт публикуется идемпотентно серверу вместе с версионными ссылками и поступает на другие устройства; каждый клиент также способен обнаружить его самостоятельно. Сервер проверяет ссылки и сохраняет сообщение, не оценивает правильность финансового результата.

Resolution — новая immutable версия с родителями всех увиденных конфликтующих ветвей. Отклонённые пользовательским выбором платежи не физически пропадают из истории синхронизации: решение указывает их исключение из финансовой проекции. Это не расширяет обычный CRUD платежей. Редактор решения разрешает только явно предложенные предметные правки и перед commit показывает последствия; результат проверяется теми же чистыми финансовыми правилами.

Третья неизвестная ветвь или два различных concurrent resolution создают новый конфликт. Два одинаковых решения с одинаковым итогом согласуются автоматически. Последующие обычные местные действия причинно зависят от local resolution; получение чужого решения сохраняет и эту зависимую работу как вариант, не сбрасывает её.

Глобальная блокировка — свойство активного набора после обнаружения, не сервера всего аккаунта: отключённое устройство продолжает работу. Получение, отправка уже сохранённых envelope, разрешение, экспорт и локальные настройки доступны. Черновик открытой формы продолжает сохранять ввод, но завершение запрещено. После последнего local resolution запись разрешается до server ack. В UI — список конфликтов, readable diff, источник/время как подсказки, предварительный итог; не универсальный raw JSON editor и не «сервер всегда прав».

### 6. Go, PostgreSQL и транспорт

Добавить самостоятельный модуль `server/`:

- `cmd/debts-server`, `cmd/debts-admin`;
- `internal/config`, `httpapi`, `auth`, `sync`, `store/postgres`;
- версионные SQL migrations и тесты; контракт и fixtures в `protocol/` на уровне репозитория.

Использовать стандартный `net/http`, `pgx/v5` с пулом и явными транзакциями. Нет финансового ORM с callback-пересчётом. Основные таблицы: `users`, `auth_methods`, `sessions`, `auth_challenges`, `recovery_codes`, `datasets` (generation, committed sequence, hash anchor), `changes`, `heads`, `conflict_reports`, `snapshot_manifests`. Версии хранятся как валидированный JSONB вместе с индексируемыми владельцем, ID, generation, связями и digest. Это не одна авторитетная таблица «текущий долг».

Серверные границы `/api/v1`:

| Операция | Назначение |
| --- | --- |
| `GET /capabilities` | публичные методы входа, регистрация, версии, адрес основной установки и политика бэкапов; без секретов |
| `/auth/*`, `/account/*` | вход, привязка, passkey, recovery, сеансы, подтверждение и удаление |
| `POST /sync/push` | ограниченный набор envelope; подтверждение по ID/digest, структурные ошибки отдельно |
| `GET /sync/pull` | целые группы после курсора, pinned upper bound и next cursor |
| `GET /sync/snapshot` | pinned snapshot и страницы с manifest/digest для догоняющей реплики |
| `/sync/conflicts` | идемпотентные отчёты о конфликте, решения доставляются как change-set |
| `GET /sync/events` | SSE-сигнал «появились изменения», без финансового содержимого |
| `POST /dataset/reset` | online reauth, generation reset; отдельно от удаления аккаунта |

Курсор включает generation, committed sequence и hash anchor. Для каждого account dataset последовательность выделяется под row lock внутри той же транзакции, что записывает envelope и обновляет hash chain. Не использовать обычный `BIGSERIAL` как единственное доказательство полноты: более ранняя транзакция могла бы commit позже уже выданного курсора. Страницы не разрывают atomic write-set, `pull` работает до закреплённой верхней позиции.

Группа либо записывается целиком, либо не записывается. Batch response возвращает результат каждой независимой группы, но зависимости не подтверждаются раньше родителей. Публиковать уведомления только после commit. SSE выбран вместо WebSocket: нужна односторонняя инвалидизация, реальные данные идут через pull; reconnect и сигнал потери соединения всегда запускают catch-up. Для одного Go-процесса достаточно подписок в памяти, для нескольких можно добавить PostgreSQL LISTEN/NOTIFY; корректность от канала уведомлений не зависит.

Клиент сначала сохраняет/применяет полученные группы и next cursor одной локальной транзакцией. Ошибка применения не продвигает cursor. Для snapshot данные пишутся в staging с проверкой manifest, затем атомарно заменяется только базовая часть проекции с повторным согласованием местных pending/known divergent версий. Не использовать wipe активного набора. Если общий предок недоступен, сохранять варианты и recovery, а не выдумывать безопасный merge.

В первой версии не выполнять автоматический GC версий текущего поколения: tombstones и необходимые causal parents сохраняются; рост контролируется лимитами и операторским мониторингом. Протокол сразу предусматривает snapshot fallback, но не обещает бесконечную совместимость. Будущая compaction не удаляет open conflict/resolution dependencies и маркеры объединений.

### 7. Авторизация без писем

Не переносить ранее обсуждённый Better Auth в отдельный Node-сервис: backend остаётся Go. Использовать поддерживаемые библиотеки для протоколов: `golang.org/x/oauth2` для OAuth2, `go-webauthn/webauthn` для WebAuthn и `golang.org/x/crypto/argon2` для Argon2id. Версии фиксируются в `go.mod` после проверки лицензий и поддерживаемой Go-версии; не реализовывать криптографические примитивы самостоятельно.

Сеансы — случайные opaque cookies с `Secure`, `HttpOnly`, ограниченными Path/Domain и `SameSite=Lax`, сервер хранит hash токена. Финансовые API, logout и admin-user flow требуют соответствующих полномочий; все изменяющие cookie-auth запросы проверяют Origin и CSRF. Только настроенный origin, без wildcard CORS. Браузерная offline identity не является действительным серверным сеансом и позволяет лишь открыть прежнюю реплику.

OAuth — authorization code, уникальный state, привязка к попытке и браузерному сеансу, фиксированный callback, PKCE там, где поддерживается выбранным провайдером. Получать идентичность через официальный endpoint провайдера; ключ аккаунта `(provider, stable subject ID)`, не email или username. Использовать минимальные scopes и не сохранять provider access token после получения идентичности, если не нужен для завершения процедуры. Не логировать OAuth-ответы. Callback с попыткой login не превращается автоматически в link; link требует существующего недавно подтверждённого аккаунта и одноразового намерения.

Passkey: фиксированные RP ID/origin, server-side одноразовые challenge с TTL и purpose, обязательная проверка пользователя. Создание только для аутентифицированного пользователя после recent reauth, вход по зарегистрированному credential. Проверку origin, подписи, challenge и свойств authenticator делает библиотека; счётчики обрабатывать с учётом синхронизируемых passkey, не выдумывать собственный запрет по любому нулевому sign counter. Регистрация нескольких ключей, удаление последнего способа запрещено в серверной транзакции.

Email/пароль: нормализованный login identifier с уникальностью, email не verified. Нет email reset, magic links или автоматического account linking. Argon2id с индивидуальной солью и версионированными параметрами, параметры не слабее актуального рекомендуемого минимума и проверяются нагрузочным тестом. Ограничить длину до хеширования и общий concurrency ресурсоёмких проверок. Восстановление — account identifier + одноразовый криптографически случайный high-entropy code; хранить hash, применить и отменить старые sessions/recovery challenge одной транзакцией. Recent reauth имеет ограниченный срок и не равен просто живому cookie.

Уникальность provider subject, выдача recovery code, отзыв sessions, привязка и удаление аккаунта транзакционны и устойчивы к повтору/гонке. Ошибки входа/recovery не раскрывают существование email. CLI создания пользователя не выводит пароль и читает его с терминала без echo.

### 8. Подключение гостя, импорт и очистка

Подключение — resumable transfer session с постоянным transfer ID, account ID, исходным guest dataset ID и снимком его версии. Пока идёт перенос, изменения источника не принимаются в передаваемый снимок молча: UI завершает запись черновиков, закрепляет snapshot и временно блокирует окончательные финансовые изменения до завершения/отмены перехода. Ошибка возвращает доступ к исходнику. Server ack всего transfer проверяется перед очисткой исходных финансовых данных. Гостевые черновики не переносятся и не удаляются без отдельного подтверждения.

При одинаковых UUID и одинаковом содержимом запись дедуплицируется. При одинаковом UUID, разном содержимом и неизвестном предке — conflict, не выбор по дате. Разные UUID с одинаковым именем сохраняются. «Использовать данные аккаунта» сначала скачивает целый snapshot в целевой namespace; только затем с отдельным подтверждением убирает guest financial data. «Пока не подключать» не отправляет guest финансов. Вход и выбор active dataset — разные шаги; без подтверждения user остаётся в guest.

Удаление копии/выход останавливает coordinator, отзывает активность других вкладок и закрывает DB connections до удаления базы; поздние ответы проверяют activation token. При pending/conflict сначала экспорт или явное подтверждение потери. Экспорт не считается выполненным только потому, что был начат download; пользовательское подтверждение удаления остаётся отдельным шагом. При выходе офлайн JS не может сам стереть HttpOnly cookie: реестр устанавливает logout fence, запрещающий автоматическое открытие аккаунта по оставшемуся cookie, а при восстановлении связи завершается серверный logout с очисткой cookie до нового входа. Намерение отзыва привязано к прежнему публичному session ID и не должно отзывать новый сеанс после смены пользователя. Это не удалённое стирание и не обещание немедленного серверного отзыва без сети.

Очистка всего финансового набора аккаунта требует online reauth и row lock dataset: увеличить generation, записать reset marker, старые push отвергать как `generation_changed`, старые данные исключить из текущей выдачи. Незавершённые старые данные сначала сохранить в локальный recovery namespace, дать просмотр/экспорт и отдельный явный перенос; они не становятся новой автоматической outbox. Account deletion удаляет auth/versions и отзывает sessions, но не утверждает стирание офлайн-копий или бэкапов.

### 9. Контакты, ссылки и черновики

Новые действия живут в `entities/debt` для атомарного переноса всего связанного домена. UI форм/подтверждений — отдельные features. Сохранять прежний формат `colorValue` из палитры, не менять денежный формат ради CRUD. При переименовании цвет остаётся; одинаковые имена после sync отличать устойчивым коротким отображаемым идентификатором и финансовой сводкой.

Merge contact формирует один change-set: target сохраняет ID/имя/цвет, source получает tombstone и явный redirect, все известные `contactId`, `participants.ref`, `items.refs`, `tips.refs` заменяются без перестановки и пересчёта денег. Если source и target находятся в одном bill, операция целиком запрещена. Новая concurrent ссылка на удалённый/объединяемый контакт не применяется как dangling reference: согласование либо переносит однозначную ссылку при сохранении инвариантов, либо создаёт конфликт; при общем счёте и неоднозначной структуре обязателен конфликт.

Локальные черновики не входят в network write-set. После изменения контактов обработать их в очереди текущего namespace: удалённый контакт требует исправления, безопасный redirect обновляет ссылку. Если оба контакта есть в одном черновике, сохранить исходный payload и показать issue, не складывать оплаты/доли автоматически. У других устройств это выполняется при применении входящих контактных изменений. Финальный create всегда повторно проверяет актуальные ссылки и write gate.

### 10. Бэкап версии 4

Сохранить верхние поля `exportedAt`, `contacts`, `debts`, `debtOperations`, `bills`, `meta` и денежные значения в прежнем пользовательском формате, добавить `version: 4` и необязательный `recovery` с версиями конфликтов, неотправленными изменениями и изолированными вариантами старого поколения. Данные для восстановления не включают cookie, пароли/хеши паролей, OAuth-токены, private key, recovery code входа или авторизационные challenge. Служебный `meta.schemaVersion` не превращается в разрешение открыть account namespace.

Экспорт одной read-only транзакцией по всем участвующим таблицам активного набора. Для данных, помещённых в отдельный recovery namespace после смены поколения, отдельное действие экспортирует этот набор и все его варианты; они не должны исчезать из доступного UI. До destructive logout экспорт включает необходимые сохранённые recovery-варианты либо требует отдельного экспорта каждого с явным предупреждением.

Импорт 1–3 сохраняет прежнюю нормализацию. Импорт 4 валидирует не только массивы, но идентичности, связи, безопасные размеры, версии и структуру recovery; восстанавливает её как local-only recovery с возможностью разбора, не как доверенный server cursor/session. Вложенные варианты остаются доступными; outbox старого аккаунта не запускается. Новый явный transfer создаёт новые envelope для актуального аккаунта/generation, сохраняя UUID финансовых записей для безопасного сравнения.

Это повышает версию portable backup, поскольку прежняя версия 3 не может выразить две версии платежа и неотправленное удаление. Обычный v3-export без recovery отвергнут как единственная защита перед выходом: он мог бы сохранить только отображаемую ветвь и потерять альтернативу. Импорт непосредственно в аккаунт и сетевой replaceAll не предоставляются.

### 11. Две поставки, конфигурация и выпуск

Статический режим выбирается явным публичным build flag; серверный web-контейнер использует ту же кодовую базу и относительные `/api/v1`. Недоступный backend не превращает аккаунтную установку в guest-only сборку: local replica остаётся активной. Публичные capabilities кешируются для показа UI без сети, но не используются как подтверждение server session.

Текущий web-образ сохранить для локальной поставки; серверную конфигурацию дополнить backend image и PostgreSQL volume через Compose profile/override. Точные теги web/backend привязать к одному релизу, не полагаться на независимо плавающие `latest`. Nginx проксирует API/SSE, не SPA fallback для API, не буферизует SSE, выставляет подходящие timeouts. SW не кеширует `/api`, OAuth callbacks и приватные сетевые ответы; offline data только через IndexedDB.

Предлагаемый публичный конфигурационный контракт (документировать значения и проверку):

| Переменные | Назначение |
| --- | --- |
| `DEBTS_PUBLIC_URL`, `DEBTS_DATABASE_URL`, `DEBTS_SESSION_SECRET` | origin, PostgreSQL, серверный ключ |
| `DEBTS_REGISTRATION_ENABLED`, `DEBTS_AUTH_PASSWORD_ENABLED` | регистрация и пароль |
| `DEBTS_AUTH_GOOGLE_ENABLED`, `DEBTS_GOOGLE_CLIENT_ID`, `DEBTS_GOOGLE_CLIENT_SECRET` | Google |
| `DEBTS_AUTH_GITHUB_ENABLED`, `DEBTS_GITHUB_CLIENT_ID`, `DEBTS_GITHUB_CLIENT_SECRET` | GitHub |
| `DEBTS_PASSKEY_ENABLED`, `DEBTS_PASSKEY_RP_ID` | WebAuthn, origin строго из публичной конфигурации |
| `DEBTS_RATE_LIMIT_*`, `DEBTS_MAX_REQUEST_BYTES`, `DEBTS_MAX_ACCOUNT_BYTES` | ограничения; отключение только явным валидным значением |
| `DEBTS_BACKUP_POLICY_URL` | политика хранения копий установки |
| `VITE_DEPLOYMENT_MODE`, `VITE_MAIN_SERVICE_URL` | публичный режим сборки и предложение переезда со старого сайта |

OAuth secrets не используют `VITE_` и не передаются build args. Секреты создаёт оператор, пример окружения только с placeholders; deployment поддерживает secret file mapping в окружение без коммита секретов. При ошибочной конфигурации startup fail до готовности health endpoint. Ограничения имеют безопасные документированные значения; учитывать reverse proxy без доверия к произвольному `X-Forwarded-For`, bounded auth hashing, SSE connection caps. БД не публиковать в интернет.

Релиз сохраняет Pages с прежним base/id/start_url и публикует отдельный Go backend image. Полноценный сервис размещает оператор на заранее выбранном HTTPS-домене; этот план не покупает домен и не меняет DNS. Pages предлагает экспорт/переход/импорт и не редиректит. Новый origin означает отдельную БД, PWA и RP ID. Тексты и скриншоты не обещают «всегда только на устройстве» в серверной поставке.

### 12. Бэкапы и восстановление сервера

Документировать проверенный `pg_dump`/restore всего логически связанного набора и отдельное защищённое сохранение серверных секретов. Расписание, шифрование файлов и retention выбирает оператор. Не включать реальную финансовую нагрузку в обычные логи; логировать request ID, код проблемы и безопасные счётчики.

После restore клиент сверяет cursor generation/sequence/hash anchor. Cursor впереди восстановленной БД или несовпадающая цепочка не трактуется как отсутствие новых данных: запрашивается snapshot recovery. Сохранить не только pending, но и локально известные версии, которые сервер ранее подтверждал, а после restore утратил. Они доступны для разбора/явного восстановления, не исчезают из-за прежнего ack. Это проверяется отдельным тестом восстановления более старого бэкапа. Session revocation при restore требует операторского отзыва восстановленных сеансов, поскольку старый dump может содержать уже отозванные credentials; инструкция восстановления закрывает публичный доступ до выполнения этой процедуры.

### 13. Проверки и границы готовности

Реализация по вертикальным этапам с обязательными проверками перед следующим:

1. Dexie migration + атомарные actions в локальном режиме.
2. Pure causal merge + transport contracts и fixtures без auth UI.
3. PostgreSQL append/pull/snapshot + Go auth.
4. Несколько браузерных реплик, onboarding и conflict UX.
5. Две поставки и восстановление сервера.

Первый этап не публикует пользователю половинную синхронизацию. Включать серверные возможности только после прохождения межрепличной матрицы.

Модельные/property-based тесты проверяют permutations/duplicates, N>=3 ветви, одинаковый frontier => одинаковый согласованный результат, отсутствие потерянных операций, целые write-set, conflict + descendant edits, одинаковые и разные resolutions. Browser tests — реальные IndexedDB/Dexie, остановка после commit и до ack, две вкладки, pending/logout, migration fence, старый SW и отсутствие private API caching. Go tests — PostgreSQL, access isolation, row-lock cursor, cycles/dependencies/digest, auth races/recovery, body/rate limits, backup restore. Provider callbacks — проверяемые заглушки плюс ручной smoke на реальных настроенных Google/GitHub и passkey в поддерживаемых браузерах.

## Risks / Trade-offs

- [Собственный sync engine существенно сложнее CRUD] → ограниченный protocol v1, конечная матрица merge, explicit conflicts и обязательные модельные тесты до UI-интеграции.
- [Несогласованные деньги из разных частей счёта] → атомарные агрегаты/группы и проверки клиентской проекции, без серверного финансового пересчёта.
- [Поддельный клиент записал финансово неверное содержимое своего аккаунта] → server schema/access/size validation и клиентская доменная проверка при получении; некорректное содержимое изолируется для recovery, не ломает гидрацию и не затрагивает других пользователей. Сервер не является гарантом истинности личного учёта.
- [Глобальная блокировка мешает работе из-за одного конфликта] → наглядный разбор и офлайн-решение; это сознательный пользовательский выбор, не заменить его блокировкой одной строки.
- [Рост истории и полных before/after] → ограничения объёма, счётчики эксплуатации, pinned snapshots; не удалять причинную историю без отдельного безопасного алгоритма compaction.
- [Неподтверждённый email и отсутствие писем] → нет auto-link, есть passkey/провайдеры/recovery code; потеря всего не обещает восстановление.
- [XSS даёт доступ к локальной финансовой реплике] → обычная защита UI/зависимостей/CSP и HTTP-only session; это не сквозное шифрование и не защищённое локальное хранилище от владельца устройства.
- [Migration fence мешает откату и требует закрыть вкладки] → исходник сохраняется до commit/проверки, явная ошибка и экспорт; отсутствие автоматического downgrade документировано.
- [Смена домена разделяет данные и passkey] → определить production origin до включения passkey, перенос через файл, не изменять идентичность старой Pages PWA.
- [Восстановление БД возвращает старые сеансы] → закрытый restore с отзывом сеансов и проверяемым переподключением клиентов до открытия публичного доступа.

## Migration Plan

1. Отревьюить этот change и пересечения с `add-english-and-number-formats`; не менять его файлы в реализации этого change без отдельного согласования области.
2. Реализовать и проверить local migration, v4 backup и импорт 1–3 на фикстурах прежних версий; проверить crash/blocked/rollback. Не публиковать backend до безопасного экспорта.
3. Применить серверные SQL migrations на тестовой PostgreSQL, настроить HTTPS origin и собственные provider credentials, закрыть публичную регистрацию до smoke-проверок.
4. Проверить replay/merge/auth/restore матрицу, затем выпустить версии web/backend как единый совместимый комплект. Публичное включение регистрации — решение оператора.
5. Обновить GitHub Pages local-only сборкой с прежним PWA ID и предложением нового адреса; оставить все прежние финансовые данные доступными после локальной миграции.
6. Дать пользовательский перенос через файл и отдельную установку нового домена. Подключение guest -> account всегда явное и resumable.
7. Откат: до включения новых возможностей восстановить предыдущие образы только с совместимой схемой; после изменения IndexedDB не открывать её старым клиентом. Для пользовательского отката — экспорт на текущей версии и чистый профиль совместимого приложения; v4 не обещает чтения старыми версиями. Серверный откат — из проверенной согласованной копии с session revocation и клиентским snapshot recovery, не удаление volume.

- Операторские значения: production домен, адрес политики бэкапов, конкретные лимиты и периодичность внешнего резервного копирования. Это параметры установки, а не незакрытые правила продукта.
- Точные поддерживаемые версии Go, PostgreSQL и зависимостей зафиксировать при начале реализации по их совместимости и лицензиям; выбранные границы сервиса и протокола от этого не меняются.
