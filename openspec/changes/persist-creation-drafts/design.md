# Design

## Context

Мотивация и границы поведения — в `proposal.md` и пяти delta specs. Дизайн необходим: изменение затрагивает формы, гидрацию, хранение, транзакции создания и импорт.

Сейчас `useBillForm` держит `BillFormState` в `useState`, а `BillForm` отдельно хранит шаг. `CreateDebtForm` хранит значения собственными `useState`. Страницы создания передают цели возврата; обе формы теряют ввод при размонтировании. Название `BillDraft` в расчётах означает нормализованный вход расчёта, а не сохраняемый черновик формы: преобразования убирают пустые позиции и приводят строки к числам.

`StorageAdapter` работает с IndexedDB версии 2. Создание счёта и долгов уже использует одну транзакцию; обычный долг и его начальная операция сейчас записываются двумя вызовами. `HomeScreen` имеет отдельную раннюю ветку онбординга без долгов и счетов. Тестового раннера в `package.json` нет; его добавление не включается в изменение.

Реализованный `add-my-receipt-share` ещё не архивирован. Его дельты создания счёта и импорта учтены здесь; архивировать его нужно раньше `persist-creation-drafts`. `improve-pwa-install` меняет онбординг, поэтому блок черновиков располагается снаружи существующего `HomeOnboarding`, не заменяя карточку установки.

## Goals / Non-Goals

**Goals:** сохранить исходное состояние форм независимо от бизнес-валидации; упорядочить автосохранение и завершение формы; использовать существующие FSD и IndexedDB; не менять расчёты окончательных записей.

**Non-Goals:** универсальный конструктор сохраняемых форм, новый storage backend, согласование параллельного редактирования одной формы в нескольких вкладках. Полный продуктовый скоуп указан в предложении.

## Decisions

### 1. Отдельный store черновиков в существующей IndexedDB

Добавить `creationDrafts` с ключом `kind` (`debt` / `bill`). Запись содержит `id` конкретного сеанса черновика, `version: 1`, `updatedAt`, дискриминированный `payload`. Не смешивать черновики с `debts` и `bills`: так финансовые агрегаты и экспорт не увидят незавершённые записи.

Формат хранения объявляется в `shared/lib/storage` без импорта из features. Как и существующие доменные типы, типы черновиков доступны через публичный API `entities/debt`. Из `use-bill-form.ts` перенести только нужные типы исходного состояния, не переносить логику формы в shared. Модель черновиков остаётся внутри существующего слайса `entities/debt`, чтобы транзакции создания и черновик имели одного владельца.

Альтернатива `localStorage` проще для синхронной записи, но не позволяет атомарно завершать черновик вместе с долгом или счётом. `sessionStorage` не покрывает полный перезапуск. Persist всего Zustand-стора дублирует доменные данные и не сохраняет локальное состояние форм автоматически.

### 2. Снимок исходных полей вместо расчётного входа

Для долга хранить `contactId`, `direction`, `currency`, `amount: string`, `note`. Для счёта хранить полный эквивалент `BillFormState` и `step: 1 | 2`: оба режима, сырые суммы участников, порядок и ссылки, все позиции с id, скидку и чаевые вместе с состоянием раскрытия. Не использовать `toBillInput` или результат preview как формат сохранения. Не обрезать текст и не приводить незавершённые суммы к числам.

Производные доли, переводы и ошибки пересчитываются после восстановления существующими функциями. Не сохранять фокус, клавиатуру, шторки, picker, `pending`, `showErrors`, `saveError`, `spreadUndo` и scroll position. На десктопе шаг не влияет на раскладку, но сохраняется для следующего мобильного открытия.

Отсутствие изменения начальной формы не создаёт запись. Сравнение с начальными значениями исключает эфемерные id пустой строки; предвыбранный контактом вход сам по себе не считается вводом. После первого изменения существующий черновик сохраняется до явного удаления или успешного создания, даже если пользователь очистил поля. Это не требует автоматического удаления по эвристикам «пустоты».

### 3. Гидрация до инициализации формы и приоритет черновика

Загрузить черновики при гидрации существующей модели, отдельно отслеживая успех чтения черновиков. До результата чтения не монтировать редактируемую форму с начальными значениями: это предотвращает запись пустого состояния поверх существующего. При ошибке чтения показать ошибку и повтор, не начинать автосохранение. Неизвестная версия или повреждённая структура записи обрабатывается как ошибка восстановления, не как отсутствие черновика; удалить её можно только явным действием.

Любой вход `/new` или `/bills/new` продолжает существующий черновик соответствующего вида. Предвыбранный `contactId` применяется только при его отсутствии. Восстановленная форма показывает краткую подпись «Продолжаете незавершённый долг/счёт». Это предпочтительнее скрытой перезаписи или отдельного выбора между старым и новым вводом при каждом входе. Это принятое в плане правило для одного черновика на вид.

Контакты читаются до проверки ссылок. Если ссылка больше не существует, не создавать контакт и не подменять плательщика молча: сохранить остальные поля, показать необходимость заново выбрать отсутствующего контакта/участника и блокировать окончательное создание до исправления. Неполные пользовательские значения допустимы; несовместимая структура записи — нет.

Цель возврата берётся из текущего входа страницы, а не из сохранённого `location.state`: продолжение с главной возвращает на главную. Прямое открытие формы использует существующий безопасный fallback. Обычный запуск по манифесту остаётся на главной, новый startup redirect не нужен.

### 4. Автосохранение по изменениям, очередь вне React-компонента

Каждое изменение полей или шага немедленно передаёт полный актуальный снимок владельцу черновика; не вводить debounce и не ждать blur, размонтирования или `beforeunload`. Централизовать обновление состояния счёта и долга так, чтобы обработчики не формировали снимки из устаревшего React closure. Владелец очереди находится в модели, а не в компоненте: переход на другой экран не отменяет запись. Повторная инициализация, включая React Strict Mode, не должна запускать новую сессию или перезаписывать данные.

Записи одного черновика выполняются последовательно. Состояние модели различает актуальный снимок в памяти и последнюю подтверждённую запись. После ошибки сохраняется актуальный ввод; «Повторить» пишет последний снимок, не тот, который впервые дал ошибку. Ошибки черновика не скрывать баннером успешного сохранения окончательной записи.

На форме показывать компактный статус: «Сохраняем черновик…» во время записи, «Черновик сохранён» после commit, сообщение из спецификации и «Повторить» при ошибке. При выходе через кнопку «Назад» дождаться очереди; при ошибке оставить форму с вводом и повтором. При браузерном выходе очередь продолжает работу в модели; выгрузка процесса не даёт возможности ждать произвольные асинхронные операции. Сохранность гарантируется для завершённых транзакций, а не для ещё не записанного последнего символа.

### 5. Завершение и удаление без воскрешения черновика

Перед созданием заморозить изменения формы и остановить новые записи текущего сеанса, дождаться уже поставленных автосохранений. Добавить атомарную запись обычного долга с начальной операцией и удалением черновика. Для счёта расширить существующий `putBillWithDebts` удалением черновика только при создании; изменение существующего счёта черновики не затрагивает. Проверять `id` сеанса перед удалением, чтобы не удалить другую сессию этого вида.

Удалять черновик в той же транзакции, что и окончательные записи, через существующий подход `commitOrAbort`. Только после commit обновлять модель черновиков как завершённую и вызывать навигацию. При abort откатывать оптимистичные окончательные записи, восстанавливать возможность автосохранения и сохранять ввод. Ошибка предыдущего автосохранения сама по себе не мешает записать валидную форму: окончательная транзакция принимает актуальные значения.

Явное удаление использует ту же сериализацию и блокировку сеанса: очередь не может после удаления поставить старый снимок обратно. После успеха выйти из формы без монтирования пустого сохраняемого черновика. При ошибке удаления не скрывать его как удалённый. Одного `deleteDraft()` в `onSaved` недостаточно: завершение процесса между двумя транзакциями оставило бы запись и старый черновик.

### 6. Распределение по слоям FSD

| Слой / слайс | Изменение |
|---|---|
| `shared/lib/storage` | Типы сохраняемых снимков, store, миграция, CRUD, атомарное завершение и очистка при `replaceAll` |
| `entities/debt/model` | Состояние и гидрация черновиков, очередь сессий, интеграция с `createDebt` / `createBill`, публичный API без импорта features |
| `features/create-debt` | Восстановление полей, отслеживание ввода, статус записи и новая подпись кнопок |
| `features/create-bill` | Сохранение полного состояния и шага только в режиме создания; редактирование `bill` остаётся прежним |
| `features/delete-creation-draft` | Подтверждение удаления через существующую `ConfirmActionModal`, явные подписи и обработка ошибки |
| `pages/create-debt`, `pages/create-bill` | Ожидание восстановления, текущая цель возврата и выход после завершения/удаления |
| `widgets/home-screen` | Блок черновиков перед содержимым в обеих ветках главной; ссылки в формы, без импортов внутренних частей features |
| `app/providers` | Подключение гидрации черновиков через публичный API модели |
| Настройки, экспорт, импорт | Только уточнение связанных текстов и очистка черновиков при замене/сбросе данных |

Тексты — в колоцированных переводах. Поверхности, кнопки и шторки используют существующие токены и компоненты; новых зависимостей не требуется. Текст «Отмена» не заменяется вне создания долга/счёта и подтверждения удаления черновика.

### 7. Резервная копия и очистка

Оставить формат файла `version: 3`, исключив `creationDrafts` из экспорта. `meta.schemaVersion` отражает текущую схему БД, но не становится версией файла: текущий парсер проверяет её как число. Сохранить импорт файлов версий 1–3 и нормализацию старых счетов.

Очистку `creationDrafts` включить в транзакцию `replaceAll`, чтобы при неудачном импорте старые записи и черновики оставались вместе. Сброс данных через удаление БД уже очищает все stores, но это проверяется явно. Сброс UI-настроек не обращается к store черновиков. Пояснения экспорта, импорта и сброса должны перечислять последствия для черновиков; другие сценарии подтверждений не переименовываются.

## Risks / Trade-offs

- Завершение процесса во время незавершённой записи → запись при каждом изменении без таймера и честный статус commit; невозможно гарантировать последний символ при мгновенном принудительном завершении процесса.
- Гонка между записью, удалением и навигацией → очередь вне компонента, идентификатор сеанса, блокировка завершения и общая транзакция.
- Частые записи больших чеков → запись небольшого снимка только своего вида; проверить ввод длинного чека на телефоне, не вводить debounce без пересмотра требований сохранности.
- Старый черновик при входе из другого контакта → приоритет черновика, заметная подпись продолжения и явное удаление перед новым вводом.
- Рост версии БД исключает открытие старым приложением на том же профиле → откат через экспорт окончательных записей; черновики не переносимы через файл.
- Несколько вкладок могут редактировать один вид черновика → в этом изменении применяется последнее успешно записанное состояние; полноценное совместное редактирование не проектируется. Проверка идентификатора при завершении защищает чужую новую сессию от удаления.

## Migration Plan

1. Добавить store `creationDrafts` при `oldVersion < 3`; установить версию БД и `CURRENT_SCHEMA_VERSION` в 3. Не переписывать долги, счета и контакты. На чистой установке создать все stores последовательными шагами миграции.
2. Сохранить закрытие соединения по `blocking`, чтобы обновление не зависало из-за прежней вкладки.
3. Подключить гидрацию и формы; проверить обновление БД версии 2 с историей и счетами обоих видов, а также чистую установку.
4. Проверить экспорт и импорт копий версий 1–3, атомарную очистку черновиков, сохранность при ошибках.
5. Проверить на телефоне выгрузку установленной PWA и повторный запуск офлайн для трёх вариантов: долг, счёт одной суммой, чек. Если реального устройства нет, явно оставить эту проверку неподтверждённой в отчёте реализации.
6. При откате не понижать версию существующей БД на месте: экспортировать окончательные записи и восстановить их в совместимой версии на чистом профиле. Черновики остаются локальными данными новой версии.
